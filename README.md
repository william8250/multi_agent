# Multi-Agent Vibe Coding Workbench

**面向个人开发者的跨平台多智能体协作台：由主 Agent 统筹需求与流程，让不同平台的子 Agent 发挥各自主推模型和工具生态的优势，再以独立会话交叉评审，最终由人掌握方向和验收。**

Many developers use several AI coding products, but those products do not reliably share project context, decisions, task status, or review history. This project provides a local workspace for coordinating them through one shared project brief and a traceable workflow.

## 核心价值：跨平台主从协作与独立评审

许多多 Agent 开发方案集中在同一个模型、同一套 Agent 框架或同一个 MaaS 平台里。这样容易统一调度，却难以同时发挥不同模型的长处，也不容易使用各平台自带的 Skill、插件和工作流。

本项目采用“主 Agent + 子 Agent”的协作方式：主 Agent 维护共同项目依据、拆分阶段任务、安排平台角色并汇总结果；WorkBuddy、豆包、Codex 等平台中的子 Agent 分别承担适合自己的执行或评审工作，继续使用各自平台提供的模型与生态工具。协调台记录每次任务实际使用的平台、界面显示的模型和结果来源。

交叉评审时，各评审方使用独立会话和独立任务上下文，提交前不互相查看对方意见。每方分别给出判断和投票，再由协调流程汇总差异，交给用户复核和裁决。这样可以减少共享对话记忆、先看到他人结论所带来的相互影响，让不同平台从各自上下文出发检查同一份冻结材料。它能降低评价锚定和记忆串扰，不能保证评审绝对客观；评审依据、分歧、投票与人工决定都会保留记录。

这里的“主从”描述任务协调关系，不表示某个平台模型天然高于其他模型。主 Agent 负责组织和整合，子 Agent 按其平台能力、项目分工和成本承担工作。

## 全生命周期可见，用户随时参与打磨

协作台把需求、设计、开发、调试、评审和验收放在同一项目脉络里，持续展示已记录的任务状态、阶段成果、风险和待用户决定事项。用户可以随时补充需求、调整方向、暂停后续分发，也可以打开正在打磨的原型，在具体页面或选中的区域发表评论。评论可以提交为修改任务；协调方整理范围，Agent 产出新版本并完成检查后，在评论区回报处理结果，用户再体验和反馈。

这让不会写代码的用户也能围绕实际页面表达外观和交互意见，并跟进意见是否已处理。协作台展示的是任务和交接的留痕状态；对于需要桌面应用接力的平台，没有实时运行心跳，任务执行时长和百分比不会凭空估算，出现等待或异常时仍可能需要用户介入。

## 为什么使用它

- **先把想法说清楚**：把目标、范围、验收条件和风险整理成可持续更新的项目依据。
- **发挥平台各自优势**：把任务交给适合的平台、主推模型及其 Skill／插件生态，不强迫所有角色使用同一个模型或 MaaS。
- **让 Agent 分工**：主 Agent 统筹项目依据和流程，为不同平台的执行方、协作者和独立评审方准备范围清楚的任务包。
- **让评审彼此独立**：在评审提交前隔离会话上下文，分别记录意见与投票，减少相互影响，再由用户复核分歧与结论。
- **贯穿生命周期跟进**：在一个项目视图中查看需求到验收的阶段、任务、成果、风险和待决事项，用户可随时补充、暂停或纠偏。
- **在原型页面直接打磨**：选中具体页面区域发表评论，将审美与交互反馈转成有上下文的修改任务，并在评论区追踪处理结果。
- **保留人工把关**：重要业务决策、评审处置和最终验收由用户决定，不把模型意见或测试通过伪装成用户批准。
- **看清进展与依据**：记录任务交接、提交结果、评审意见、风险和变更，便于回看每个结论从哪里来。
- **受控应用代码**：对通过条件检查的候选代码提供本机应用、验证与恢复流程，避免评审建议未经确认直接写入项目。
- **兼容不同平台**：有稳定官方接口的平台可通过适配器接入；缺少接口的平台可先用桌面应用接力，并明确标记需要人工处理的步骤。

## 适合的工作方式

1. 在项目主页描述需求并补充共同资料。
2. 协调方整理需求、验收条件和阶段计划。
3. 主 Agent 按配置把任务交给不同平台的执行 Agent，并为评审方准备相互独立的上下文。
4. 评审方独立提交意见和投票；用户查看分歧、复核结论并处理需要人工决定的事项。
5. 用户在原型页面评论具体区域，协调方把反馈整理成修改任务；Agent 修改、验证并在评论中回复，用户继续体验打磨。
6. 对候选成果运行检查；符合条件后，再由授权用户决定是否应用和验收。

协作台管理的是协作流程和证据。Agent 的实际能力、账号权限、模型可用性和平台配额仍由各平台决定。

## 当前状态

项目处于**本机 Alpha** 阶段，已用“喜鹊 V2”无真实地图与实时语音 API 的演示版本验证需求协作、任务交接、交叉评审、结果追踪和受控源码应用。它适合个人开发者本机试用和反馈，尚未完成公网部署或正式产品验收。

当前能力边界：

- WorkBuddy 和豆包通过桌面应用接力；Mac 需要保持唤醒、解锁且应用可用。接力不是锁屏后持续运行的无人值守调度。
- Codex 本机执行和候选源码工作流按项目配置与安全条件运行；每次真实执行仍有额度、登录态和环境要求。
- 喜鹊演示不接真实地图、定位或实时语音服务。
- 当前是本机单用户工具，不提供多人在线协同、云端存储或公网生产部署保证。
- 评审记录会注明界面显示的平台和模型信息；桌面截图不能替代平台提供的可独立验证调用凭证。

## 快速开始

需要 Node.js **26.3.0**。在项目根目录运行：

```sh
cd collaboration-app
npm ci
npm start
```

然后在浏览器打开 <http://127.0.0.1:8766/>。服务默认只监听本机。测试命令为：

```sh
npm test
```

请勿把真实 API 密钥、平台凭据或私人项目资料放进示例、截图或测试输出。

## 目录结构

| 目录 / 文件 | 用途 |
| --- | --- |
| `collaboration-app/` | 本机协作台服务、用户界面、测试与功能文档 |
| `dev-intake/` | 开发前配置入口 |
| `projects/xique/` | 喜鹊演示项目的需求、设计和无密钥原型 |
| 根目录 Markdown 文件 | 协作机制、使用方式和配置 playbook |

本机数据库、运行记录、评审证据、截图、依赖缓存和环境配置不属于公开源码；根目录 `.gitignore` 已将常见本机数据及敏感材料排除。发布前仍应检查 `git status` 和待提交差异，忽略规则无法判断文件内容是否包含隐私或密钥。
